# Loophole Serve — IDE backend architecture

Loophole IDE is a full VS Code (Void) fork. Unlike the old Kilo-extension approach, the IDE
talks to **Loophole Serve**: the opencode-based `loophole serve` HTTP server from loophole-app
(`packages/cli/src/commands/handlers/serve.ts` → `ServerProcess.run`). Kilo does the same thing
(spawns `kilo serve --port 0` from its VS Code extension), and both servers speak the same
opencode protocol, so the IDE reuses it instead of maintaining its own provider stack.

Decisions (from the owner):
- **Binary**: bundled with the IDE at build time (Kilo-style), resolved from
  `<app>/resources/app/bin/loophole[.exe]`, overridable via `LOOPHOLE_SERVE_BIN`.
- **Providers/models**: the server owns configuration. The IDE fetches providers from the
  server (`GET /api/provider`, `GET /api/model`, 500+ models from models.dev) and writes API
  keys through the server config (Kilo provider-dialog pattern), instead of Void's direct
  provider settings.

## Wire protocol (verified against loophole-app@packages/protocol)

- Base: `http://127.0.0.1:<port>`, all routes under `/api/*`.
- Auth: HTTP Basic, username `loophole`, password = per-launch random secret generated by the
  IDE main process and passed to the server (Kilo's `KILO_SERVER_PASSWORD` equivalent).
- Sessions: `POST /api/session` (create), `POST /api/session/:id/prompt` (send user turn),
  `GET /api/session/:id`, `DELETE /api/session/:id`, `POST /api/session/:id/interrupt` (abort),
  `GET /api/session/:id/message/:messageID`, `GET /api/session/:id/context`, `GET /api/session/:id/diff`.
- Providers: `GET /api/provider`, `GET /api/provider/:id`. Models: `GET /api/model`,
  `GET /api/model/default`.
- Events: `GET /api/event` (SSE, `?types=...`), first frame `server.connected`, 15s heartbeat.

## Phases

- **Phase 0 (this change)**: `loopholeServe` IPC channel + connector service. Main process
  spawns/bundles the server on demand (`connect` / `disconnect` / `status`), no UI behavior
  changes; the existing direct-LLM path is untouched. Verified safe to ship: the channel is
  only used when Void explicitly asks for it.
- **Phase 1**: provider/model list over the wire (`GET /api/provider`, `GET /api/model`) shown
  in the Void settings "Add Model" flow, behind a `loophole.serve.enabled` toggle.
- **Phase 2**: chat transport switch — `sendLLMMessage` gains a server backend
  (create session → prompt → SSE `event.subscribe` → stream text back), replacing the direct
  provider calls (`electron-main/llmMessage/sendLLMMessage.impl.ts`).
- **Phase 3**: autocomplete — inline-completions provider calling the server's FIM surface
  (Inception models only, same as the CLI/desktop), plus a status-bar item mirroring Kilo's.
- **Phase 4**: build/packaging — CI fetches (or builds) the `loophole` binary and drops it
  into `resources/app/bin/` at packaging time; crash + version-mismatch handling.

## Phase 3 note: tool/thinking/todo UI transport (Kilo-style cards)

- **Source events** (`packages/schema/src/session-event.ts`, SSE `GET /api/event`, filtered per-session in `loopholeServeChat.ts`):
  `session.tool.input.started/delta/ended` (raw input JSON stream), `session.tool.called` (parsed `input`), `session.tool.progress` (ephemeral metadata), `session.tool.success` (`content: Content[]` + `metadata`), `session.tool.failed` (`error.message`, `content?`, `metadata?`), `session.compaction.started/delta/ended/failed`. Streaming signal = ephemeral deltas; `ended/called/success/failed` are the full-value boundaries. File (non-text) output parts are dropped.
- **Hooks** (`common/sendLLMMessageTypes.ts` → `sendLLMMessageService.ts` → `sendLLMMessageChannel.ts` → `llmMessage/sendLLMMessage.ts`/`loopholeServeChat.ts`): optional `onTool` (ordered `ServeToolState[]`, merged per call id) and `onCompaction` (`ServeCompactionState`), keyed by `requestId` alongside `onText`/`onFinalMessage`. Reasoning reuses `onText.fullReasoning`; todos ride the tool stream (`todowrite` input `todos: [{content, status}]` / result `metadata.todos`) and are derived in the UI — no separate todo event, same as Kilo.
- **State** (`browser/chatThreadService.ts` + `common/chatThreadServiceTypes.ts`): snapshots merge into the live `llmInfo.serveTools` stream state and commit as additive optional `serveTools`/`compaction` fields on the assistant `ChatMessage` (old threads lack them — renders nothing; the direct-LLM path never sets them).
- **UI** (`browser/react/src/sidebar-tsx/tool-ui/`): `ThinkingBlock.tsx` (collapsed "Thinking" header + animated status, expandable `ChatMarkdownRender` body, auto-collapses when tools/text start, re-expandable), `ToolCard.tsx` (`StatusIcon` spinner→check/error, title + file/command/query/url subtitle, expandable input/output incl. edit snippet & bash command special cases, `CompactionBanner`), `TodoList.tsx` (checklist rows: pending/in_progress/completed/cancelled icons, done/total, active item, open by default). Wired in `SidebarChat.tsx` (`AssistantMessageComponent` + streaming bubble order: compaction → thinking → tools/todos → text).
- Behind existing `loophole.serve.enabled`; old direct-LLM path untouched.

## Phase 5 note: sessions, slash commands, checkpoints, permissions, usage, voice

- **Sessions browser**: `GET /api/session` list via `loopholeServeChannel.sessions` → `ILoopholeServeService.sessions` → `ServeSessionsBrowser.tsx` (search, relative time, rename/fork/delete). History import uses `GET /api/session/:id/context` (active post-compaction window — complete, no pagination cursor; full transcript pagination is truncated at the 200-message first page) mapped best-effort into Void `ChatMessage[]` (`user`→user, `assistant` text/reasoning/tool parts→assistant + `serveTools`, completed `compaction`→compaction banner; metadata types skipped) in `chatThreadService.importServeSession`, bound via additive `thread.state.serveSessionId`/`serveUsage`. Later turns reuse the bound session (`sendLLMMessage.serveSessionId` → `loopholeServeChat` skips create and reports new ids via `onServeSession`); the prompt still sends only the new user turn because the server owns history. `duplicateThread` clears the binding; `deleteThread` drops pending permissions.
- **Slash commands + skills**: `GET /api/command` + `GET /api/skill` → `useServeSlashEntries` (`:skill` suffix on name collisions, Kilo-style); `/` menu in the composer with arrow-key nav; picking inserts `/name ` and Enter runs `POST /api/session/:id/command` (args = trailing text) or `POST /api/experimental/session/:id/skill`, auto-creating/binding a serve session when needed.
- **Checkpoints / rewind**: `ServeCheckpointPanel.tsx` lists user messages (`GET /api/session/:id/message`) and stages with `POST .../revert/stage { files: true }`, previews `files` from the `Session.Revert` response, then commits (`POST .../revert/commit`) or undoes (`DELETE .../revert`).
- **Permission cards**: `permission.asked` (ephemeral) is bridged in `loopholeServeChat` → `onPermission` → `chatThreadService` pending store → `ServePermissionCard.tsx` (Allow once/always → `once`/`always`, Deny → `reject`) via `POST /api/session/:id/permission/:requestID/reply` (endpoint exists, fully wired) + GET-list backfill on bind.
- **Usage chip**: `ServeUsageChip.tsx` renders `Session.Info.cost/tokens` on bind and live `session.usage.updated` via `onUsage` → `thread.state.serveUsage` (↑ in / ↓ out / $ cost, tooltip breakdown). `GET /api/experimental/usage/limits` is account-level (OpenCode Console) — intentionally NOT used per-session.
- **Voice / mic**: server-side dictation via `GET /api/experimental/voice/models` + `POST /api/experimental/voice/session` (WebSocket transport only; webrtc-only models like `gpt-live-1` are skipped) → main-process `ws` proxy in `loopholeServeChannel` (browser WebSocket cannot set `Authorization` headers; proxy dials with the ephemeral token and relays frames) → `useServeVoiceRecorder` (16kHz PCM16/base64 chunks; provider-shaped JSON for OpenAI/xAI vs Google; transcript extraction covers `conversation.item.input_audio_transcription.delta/completed` + generic `transcript`/`delta`/`text` shapes) → live text into the composer; stop/Enter sends through the normal serve chat path. `getUserMedia` denial shows a notification explaining to enable the mic. Serve mode replaces the local-model mic button; direct-LLM mode keeps the local button untouched.
